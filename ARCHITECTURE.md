# Архитектура Рубежа — ревью и целевая схема
## Фактическое состояние
Доступны каталог JSON, контракт, Python-проверки и генератор ассетов. Это НЕ реализация сети, C#-игры или C++-расширения. Исходный пакет этапа 0 недоступен; полного репозитория, бинарников, CI и git нет. Всё ниже — обязательная архитектура будущей реализации, не заявление о наличии модулей.

## Границы модулей

    Клиент C#: ввод → InputCommand / CommandRequest
          ↓ ограниченный транспорт (аутентификация вне клиента)
    Сервер C#: сетевой декодер → ограниченная очередь матча
          ↓ единственный исполнитель tick 64 Гц
    Авторизация → каталог/парсер → квота/идемпотентность → правила матча
          ↓ пакет команд симуляции
    C++ GDExtension: Movement + HitQuery + LagHistory
          ↓ результаты без прав и побочных сетевых вызовов
    Сервер C#: урон/экономика/бомба/модули → журнал/commit
          ↓ персональный фильтр видимости для снимков И событий
    Клиент C#: reconciliation → interpolation → UI/VFX/звук

C# владеет аккаунтами, экономикой, раундами, квотами, разрешениями, RNG/seed выстрела и окончательным решением об уроне. Клиент не передаёт готовый hit, здоровье, деньги или список целей как истину. C++ владеет плотными фиксированными буферами движения/хитбоксов, выполняет ограниченные запросы, возвращает результаты. Параметры скорости и оружия передаёт сервер. Локальный C++ прогноз не даёт полномочий серверу. Wallhack — штатная механика Sandbox, а не доступ к чужой памяти.

## C# ↔ C++ и владение памятью
Объекты GDExtension через Godot ClassDB/RefCounted; не делать предположений о совпадении layout C# struct и C++ struct. Явная версия протокола, единицы, порядок полей; для batch использовать PackedArray с проверкой длин/NaN/границ. Копии через границу измерять; не передавать указатели на перемещаемую GC память. Один владелец каждого буфера, фиксированные ёмкости, Dispose/освобождение в остановке матча. История хитбоксов ограничена числом игроков и окном rewind, например 200 мс как начальная гипотеза. Время клиента ограничивается серверным окном, будущее отклоняется. Перемотка — отдельные исторические данные, не изменение живой SceneTree. Исходников нет: отсутствие утечек НЕ доказано.

## Потоки
SceneTree и Godot Physics доступны только в разрешённом потоке. Сетевой worker декодирует/проверяет длины, пишет в bounded очередь; не мутирует состояние матча. Один tick-владелец состояния, сеть читает неизменяемые снимки. Native worker допустим только для собственных данных без Node/PhysicsServer. Не создавать второй звуковой mixer поверх существующего потока Godot; фоновые задачи ограничить декодированием/загрузкой. Отмена, timeout, drain и join обязательны. Никаких fire-and-forget задач на уничтоженные объекты.

## Сеть
Предлагается ENet/UDP для игровых сообщений, HTTPS для аккаунтов/каталога; конкретные версии и транспорт ещё не реализованы. Input имеет sequence/tick; server обрабатывает по порядку с bounds, snapshots содержат ack. Клиент хранит ограниченную историю ввода, при расхождении откатывает прогноз и повторяет неподтверждённое. Оружие, отдача, разброс, rate of fire и результат попаданий проверяются сервером. Надёжные команды идемпотентны; ненадёжные снимки не забивают канал устаревшими данными. Budget пакета задаётся до реализации, тестируются loss/reorder/duplicates/MTU.
Скрытые противники исключаются из payload, а не маскируются клиентским шейдером. Одинаковая политика для impacts, audio events, status и spectator. Пакеты разных клиентов не разделяют отфильтрованный mutable буфер. Авторизация lobby не даёт игрового admin.

## Консоль
JSON — один источник метаданных для C# парсера, Tab/help/noob и серверной валидации. Текст → токены с пределами → разрешение канонического модуля → typed values → права/режим/sv_cheats → проверка состояния/квот → атомарный commit → ответ. Клиентская проверка лишь UX. set редактирует будущий профиль, не действующий lease. Публичный status не раскрывает закрытые детали.
Повторы связываются с accountId из сессии и payload hash. Квоты/эффекты/решение записываются одной транзакцией. Ошибка persistence до commit не публикует эффект. Неясный результат commit сначала восстанавливается, не повторяется вслепую. Журнал ограничен admission cap; копии ответа вытесняются безопасно. Правила конкретизированы в docs/CONSOLE-CONTRACT.md; Python — тестовый эталон, НЕ альтернатива обязательному C# серверу.

## Производительность и ошибки
На tick нельзя LINQ, boxing, форматирование строк, задачи на каждый выстрел и растущие List. Использовать заранее выделенные input/snapshot/native buffers, пул VFX с пределами. Подтверждать профилем managed allocations, GC паузами, p95/p99 tick. Это рекомендации, не найденные реальные аллокации: кода нет. Логи структурированные и bounded, audit мутаций не теряется; overflow отказывает до изменения состояния. Ошибки клиента безопасны и не содержат stacktrace/секретов. Никаких shell/eval команд из консоли.

## Ассеты
Python/bpy создаёт собственную геометрию, UV-атлас, object animations, sockets. У каждого оружия три отдельных GLB (LOD0/1/2), один материал, одна встроенная текстура в каждом. Переключатель LOD в Godot ещё нужно реализовать по метаданным/дистанции: glTF не стандартизует переключение LOD, три файла не означают готовый переключатель. .blend хранит LOD0; генератор воспроизводит остальные. Runtime geometry generator отсутствует — Blender работает только offline.

## Проверяемый offline-запускатель
tools/run_weapons.py запускается пользователем локально: тесты → probe_api.py → пилот → независимая GLB-проверка → при --full полный набор → повторная проверка. subprocess получает список аргументов с shell=False, таймауты, потоковый лог. Рабочий каталог результата создаётся новым. API-probe проверяет необходимые поля экспортёра/NLA и object Action Slot. Эта проверка НЕ доказывает корректность всего bpy конвейера; именно поэтому пилот обязателен. Графика и игровой сервер не зависят от Python в runtime.
